# 原型方法与保真度

> 性质：**设计方法基线**。用于决定“做什么原型、测什么、何时停”，不替代 Penpot 操作规范。
>
> 证据边界：本文来自 HCI 原型研究与成熟实践，属于方法依据，**不是 Penpot API 实测**。Penpot 能力仍以 `docs/penpot-mcp/` 和 `verification/` 为准。

## 1. 先写四句话

任何原型开始前，先用四句话约束范围：

1. **问题**：这次要回答哪一个问题？只能有一个。
2. **假设**：我们相信用户会怎样、为什么？
3. **证据**：什么行为能支持或推翻这个假设？
4. **决策**：结果出来后，保留、修改还是放弃？

四句话写不出来，说明还不该画高保真。原型的价值是**过滤错误想法**，不是提前制作成品。

## 2. 保真度按问题选择

保真度不是一根“低—高”滑杆，而是交互性、表现完整度、功能完整度的组合。用问题选保真度，不要用“像不像成品”选。

| 要回答的问题 | 建议形态 | 适合观察 | 不应承担 |
|---|---|---|---|
| 信息架构、术语、流程是否成立 | 纸面/灰盒流程 | 找得到、看得懂、顺序是否合理 | 视觉精修、代码落地 |
| 关键任务能否走通 | 可点击线框 | 路径、分支、返回、失败恢复 | 品牌细节、真实数据 |
| 视觉层级、密度、品牌是否成立 | 高保真静态稿 | 扫读、层级、对齐、响应式布局 | 真实后端、复杂动效 |
| 复杂交互、时序、错误恢复 | 高保真可交互原型 | 状态切换、延迟、撤销、重试 | 需求是否值得做 |
| 服务、环境、现场体验 | 体验原型/角色扮演 | 上下文、协作、物理约束 | 像素级 UI |

规则：

- 低保真回答结构问题，高保真回答表现问题；不要让高保真掩盖结构错误。
- 混合保真度是合法选择：关键路径可点击，边缘页面用静态稿。
- 原型越像成品，用户越不愿意批评；需要明确告诉参与者“这是草稿，请挑问题”。

## 3. 原型计划模板

```text
问题：这次只回答：
假设：我们相信：
保真度：纸面 / 灰盒 / 可点击 / 高保真静态 / 高保真交互 / 体验原型
理由：为什么这个保真度足够，且不多做：
任务：参与者要完成：
成功信号：看到什么算支持假设：
失败信号：看到什么算推翻假设：
不测：这次明确不测：
决策人/时间：结果由谁在什么时候决定：
```

## 4. 形成性测试的最小流程

1. **准备任务**：用用户语言写任务，不写操作步骤，不暗示答案。
2. **少量用户**：形成性测试常用 5 名左右；目的是发现问题，不是统计显著性。高风险场景增加样本或引入专家审查。测试执行、指标和报告模板见 [`usability-test.md`](usability-test.md)。
3. **主持**：先说明“没有正确答案，原型是草稿”；提示“继续想”而不是替用户操作。
4. **观察**：记录完成/未完成、错误、卡点、原话、求助次数；时间只作为辅助信号。
5. **收尾**：问“最困惑的是什么”“你会怎么向同事描述这个功能”，不要只问“喜不喜欢”。
6. **分级**：阻断 / 严重 / 一般 / 建议；每条问题写明证据和影响范围。

不要在同一轮里同时验证信息架构、视觉品牌和代码可行性；一轮只回答一个层级的问题。

## 5. 原型后必须做决策

每个原型结束都要留下：

- 支持/推翻假设的证据；
- 保留、修改、放弃的结论；
- 下一轮只改什么；
- 哪些问题被明确移到后续验证。

没有决策记录的原型，只是一次演示。

## 6. 常见失败

| 现象 | 原因 | 处理 |
|---|---|---|
| 高保真做了很多版，仍不知道是否可用 | 没有先写问题/假设 | 回到第 1 节，先写四句话 |
| 用户只说“挺好看” | 任务太泛，或原型太像成品 | 改成具体任务；明确这是草稿 |
| 测试变成操作教学 | 主持人在救场 | 记录卡点，不替用户完成 |
| 一轮改十几个变量 | 同时测结构、视觉、交互 | 拆轮次，一轮一个层级 |
| 原型通过但上线失败 | 只测了静态画面，没测状态/异常 | 补 `states.md` 的状态矩阵 |
| 没有结论 | 没写成功/失败信号 | 测试前先写决策规则 |

## 7. 验收清单

- [ ] 只回答一个问题，且问题写在文档里
- [ ] 保真度有理由，不是“默认高保真”
- [ ] 成功信号和失败信号在测试前已写
- [ ] 任务脚本不包含操作步骤和答案
- [ ] 记录了完成/错误/卡点/原话，不只记录喜好
- [ ] 测试后给出保留/修改/放弃的决策
- [ ] 明确哪些问题不在本轮验证
