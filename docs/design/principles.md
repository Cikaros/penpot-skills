# 设计原则

> 性质：**项目规范基线**。可被具体产品覆盖，但覆盖必须写在文件里，不能靠默契。

## 1. 判断优先级

冲突时按此顺序取舍：

1. **可用**：能看懂、能点到、能读清。
2. **一致**：同类元素同一种做法。
3. **可维护**：能落到组件与 token。
4. **好看**：在前面三条都满足之后再谈。

反过来做（先好看）几乎必然返工。

## 2. 与 AI 协作的十条

完整的输入契约、证据、评审门与隐私边界见 [`ai-collaboration.md`](ai-collaboration.md)。下面只保留高频提示原则。

摘自 Penpot 官方《Good prompting practices (design)》，并按本仓库语境改写：

1. **角色要有边界**：写"资深产品设计师，懂设计系统与 WCAG；无数据时不替用户做业务决策"，不要写"有创意的设计师"。
2. **用结构化简报代替散文**：上下文 / 目标 / 输入 / 约束 / 验收。
3. **图片要指方向**：说清看哪一块、忽略哪一块，否则模型会平均用力。
4. **喂规则而不是链接**：颜色只用哪套 token、字号不越级、组件用变体。
5. **要变换，不要"成品"**：说"提升层级、去边框、按 token 归一键距"，不要说"做得现代一点"。
6. **转代码要说栈**：框架、样式方案、token 到 CSS 变量的映射，禁止魔数。
7. **要理由**：每次改动说明取舍与被放弃的方案。
8. **迭代**：分析 → 提案 → 反馈 → 落地，不要 one-shot 重画。
9. **给负向约束**：不加新导航、不动视觉识别、不假设业务规则。
10. **利用结构化数据**：token、SVG、开放格式可精确读取，优先读结构而不是靠截图猜。

## 3. 可访问性基线

> 完整的设计期清单、标注表和证据边界见 [`accessibility.md`](accessibility.md)。本节只保留不可协商的硬线。

- 正文对比度 ≥ 4.5:1；大号文本（≥ 24px 或 ≥ 19px 粗体）≥ 3:1。
- 触控目标不小于 44×44（WCAG 2.2 最低要求为 24×24，移动端按 44 执行）。
- 焦点可见：焦点环 2px，与背景对比 ≥ 3:1。
- 不只用颜色传达状态（错误同时给图标或文案）。
- 正文不小于 14px；金融、表单类场景不小于 16px。

## 4. 什么时候不该改

- 没有数据支撑的"业务决策"（改流程、改信息架构）。
- 用户明确保护的区域（品牌标识、导航结构）。
- 为了"更现代"而替换成套组件。
- 无法在现有 token/组件内表达的样式——先补体系，再改页面。

## 5. 评审三问

每次交付前自问：

1. **它解决了哪个具体问题？** 说不出就是没做对。
2. **换一个屏幕尺寸还成立吗？** 不成立说明用了绝对值拼接。
3. **下一个人能维护吗？** 不能说明该抽组件或补 token。
