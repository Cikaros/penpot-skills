# 可用性测试执行规范

> 性质：**项目方法规范**。`prototyping.md` 决定“用什么原型回答什么问题”，本文决定“测试怎么执行、证据怎么记、结论怎么落到决策”。
>
> 证据边界：本文是方法规范，不是 Penpot API 结论。测试结果必须带参与者、任务、日期和原始记录。

## 1. 什么时候做，什么时候不做

适合做：

- 关键任务路径首次成型，需要发现结构性卡点；
- 同一任务有两种方案，需要选一个；
- 上线前要确认错误恢复、空态、权限态是否可理解；
- 组件或导航改动可能影响既有习惯。

不适合做：

- 还没有明确任务，只想收集“意见”；
- 只是想证明方案正确；
- 需要统计显著性，但样本、抽样和指标都没有设计；
- 用测试替代业务决策、法务判断或真实数据分析。

## 2. 测试计划模板

```text
决策问题：这次测试后要决定什么？
目标用户：角色、经验、使用场景、样本来源
原型/环境：保真度、设备、数据、已知缺陷
任务：3–5 个，按真实优先级排序
成功标准：完成、部分完成、失败的可观察定义
关键指标：任务成功率、严重错误、求助次数、用时、SEQ（可选）
样本：人数、分组、招募方式；说明不能代表总体
主持：谁主持、谁记录、是否盲测
隐私：录制/保密/退出方式
时间：日期、每场时长、地点/远程工具
```

样本量按风险和决策成本定。形成性测试常用 5–8 人/用户群，用于发现问题，不用于统计推断；总结性测试需要独立抽样与统计方案。

## 3. 任务设计

- 用用户语言写目标，不写操作步骤。例：“请找到上次保存的车辆并修改保险到期日”，不要写“点击右上角设置”。
- 一个任务只验证一个主要路径；复杂流程拆成连续任务。
- 任务顺序避免前一个任务泄露后一个答案；必要时准备两套顺序。
- 提供真实内容或接近真实的占位内容；不要用 `Lorem ipsum` 测理解。
- 明确起点、终点和允许的求助方式。
- 为失败准备观察点：用户是否发现错误、是否知道如何恢复、是否丢失输入。

反例：

| 坏任务 | 问题 | 改法 |
|---|---|---|
| “试用一下这个页面” | 没有目标 | “请添加一辆车并确认保存成功” |
| “点击新增按钮” | 泄露操作路径 | “请添加一辆车” |
| “看看这个设计好不好” | 只能得到喜好 | 改成具体任务 + 追问困惑 |
| “完成注册并绑定银行卡” | 混合多个决策 | 拆成注册、绑定两个任务 |

## 4. 主持脚本

开场：

1. 说明目的：测试产品，不是测试人。
2. 说明原型是草稿，允许批评，允许随时退出。
3. 说明录制/记录方式和隐私边界。
4. 请参与者尽量边做边想，但不强求。

主持规则：

- 先沉默观察，至少等 10–15 秒再提示。
- 提示用“你接下来会怎么做？”“你看到了什么？”，不要给答案。
- 用户求助时先问“你期望这里发生什么？”，再决定是否救场。
- 记录原话、停顿、误点、返回、放弃，不只记录最终结果。
- 不纠正用户的审美偏好；只追问影响任务的理解和操作。
- 结束后问“最困惑的是什么”“你会怎么向同事描述这个功能”。

## 5. 观察与指标

最小记录表：

| 字段 | 说明 |
|---|---|
| 参与者 | 匿名 ID；角色/经验；不是姓名 |
| 任务 | 任务编号与版本 |
| 结果 | 完成 / 部分完成 / 失败 / 放弃 |
| 严重错误 | 会导致数据错误、重复提交、无法恢复的操作 |
| 求助 | 次数与类型（提示/代操作） |
| 用时 | 从任务开始到完成/放弃；仅作辅助 |
| 卡点 | 时间点、界面位置、用户原话 |
| SEQ | 单任务难度 1–7；可选，需在任务后立即问 |
| 备注 | 设备、网络、原型缺陷 |

指标解释：

- 任务成功率必须写清“完成”的判定；不要用“看起来完成了”。
- 用时受熟悉度、设备、网络影响，不与成功率混成一个分数。
- SEQ/SUS 是主观量表，不能替代行为证据；没有基线时不要编阈值。
- 小样本只报告“观察到的问题”，不要写“X% 用户会……”。

## 6. 严重度与决策

| 级别 | 判定 | 处理 |
|---|---|---|
| 阻断 | 主任务无法完成，且无替代路径 | 本轮必须修，修前不进入开发 |
| 严重 | 可完成但会丢数据、重复提交、误入危险操作 | 本轮修，或加明确防护 |
| 一般 | 明显绕路、理解成本高，但有可行路径 | 排期修，记录影响范围 |
| 建议 | 偏好、措辞、视觉细节 | 进入 backlog，不阻塞 |

决策规则在测试前写死：

- 同一阻断问题在至少 2 名同群参与者出现，或 1 名出现且造成不可恢复后果：必须修。
- 只有 1 名出现且可自行恢复：标记为待复核，不直接改全局流程。
- 方案 A/B 比较时，先看任务成功与严重错误，再看用时和偏好；不能只按“更喜欢”选。

## 7. 报告模板

```text
标题：<功能> 可用性测试（<日期>）
决策问题：
方法：样本、任务、原型版本、设备、限制
结论：保留 / 修改 / 放弃；下一步只改什么
关键发现：
  - 级别 | 任务 | 证据（原话/行为）| 影响 | 建议
通过项：哪些假设得到支持
未覆盖：哪些没有测，为什么
附件：任务脚本、原始记录、录制链接（受控）
```

报告里必须区分：

- **观察**：用户实际做了什么；
- **解释**：我们为什么认为这是问题；
- **建议**：准备怎么改；
- **证据强度**：样本、场景、是否可复现。

## 8. 可访问性补充

- 至少安排一名键盘用户；有条件时安排读屏用户，不要用“闭眼模拟”代替。
- 任务要覆盖焦点顺序、错误提示、弹窗关闭后焦点归位。
- 记录焦点是否可见、是否被粘性头/浮层遮挡。
- 200% 缩放和移动端目标尺寸单独检查；不要只在桌面默认缩放下测。
- 可访问性问题按阻断/严重/一般分级，不因“视觉上正常”而降级。

## 9. 验收清单

- [ ] 决策问题在测试前已写
- [ ] 任务用用户语言，不含操作步骤
- [ ] 成功/失败判定可观察
- [ ] 样本和限制写清，没有统计过度声明
- [ ] 主持人不救场，记录原话和卡点
- [ ] 严重度有统一标准
- [ ] 报告包含观察、解释、建议和证据强度
- [ ] 至少覆盖键盘路径；适用时覆盖读屏和缩放
- [ ] 测试后给出明确的保留/修改/放弃决策
